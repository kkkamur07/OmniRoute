## 1. गोष्टी कुठे असतात

- **किट.** `packages/ui-kit/src` हे `packages/ui-kit/UPSTREAM.md` मध्ये निश्चित केलेल्या commit वरील upstream `src/` ची byte-for-byte प्रत आहे (याच फाइलमध्ये परवान्याची अधिकृतताही नोंदवलेली आहे); `PATCHES.md` मध्ये स्थानिक patches दिले आहेत (एकही नाही). हे source म्हणून वापरले जाते, build शिवाय: `next.config.mjs` ते transpile करते आणि `tsconfig.json` `@omniroute/ui-kit` → `packages/ui-kit/src` आणि `@omniroute/ui-kit/*` → `packages/ui-kit/src/*` असे mappings करते (`vitest.config.ts` आणि `vitest.mcp.config.ts` मध्येही हेच alias आहेत). किट component त्याच्या subpath द्वारे (`@omniroute/ui-kit/table`, `@omniroute/ui-kit/page-header`…), `@omniroute/ui-kit` barrel द्वारे कधीही import करू नका: barrel प्रत्येक importer मध्ये प्रत्येक component (date picker सहित) आणतो. किट stylesheet `src/app/globals.css` द्वारे समाविष्ट होते (`@import "../../packages/ui-kit/src/ci-styles.css"`, पूर्ण sheet: core `ci-ui.css` तसेच प्रत्येक pattern family).
- **Tokens.** `packages/ui-kit/src/ci-tokens.css` मध्ये `--ci-*` tokens घोषित केले आहेत; `src/app/globals.css` त्यांना legacy OmniRoute नावांशी (`--color-*`, `--radius-*`, `--font-sans`/`--font-mono`, `--table-*`, `--orch-status-*`, `--color-fd-*`) जोडते, त्यामुळे विद्यमान `var(--color-*)` reads आणि Tailwind utilities कार्यरत राहतात. नवीन code मध्ये Tailwind utilities (`bg-surface`, `text-text-muted`, `border-border`, `text-success`, `bg-success-bg`, `bg-chart-1`…) किंवा kit classes वापरा — hex value कधीही वापरू नका (`tests/unit/design-kit-bridge.test.ts` हा bridge अंमलात आणते). `text-primary` हे `--text-color-primary` द्वारे `--color-primary-ink` वर resolve होते, त्यामुळे primary text वाचनीय राहतो, तर `bg-primary`/`border-primary` accent surface ठेवतात: Editions अंतर्गत ते किटचे `--ci-color-accent-active` आहे (light मध्ये गडद copper `#99562f`, dark मध्ये copper accent); Classic अंतर्गत light मध्ये lime-800 आणि dark मध्ये lime accent. Chart series `--color-chart-1` … `--color-chart-8` वापरतात; प्रत्येकासोबत text-safe `--color-chart-N-ink` आणि opaque `--color-chart-N-subtle` chip tint असतो, आणि त्यांची नेमणूक kit series order (`ciChartSeriesOrder`) नुसार केली जाते.
- **Themes.** `<html className="ci-theme">` (`src/app/layout.tsx`) document ला kit theme मध्ये opt करते. Preference `light`, `dark` किंवा `system` असते (`src/shared/constants/appConfig.ts` मधील `THEME_CONFIG.defaultTheme = "system"`; `system` हे `prefers-color-scheme` चे अनुसरण करते). `src/store/themeStore.ts` मधील `applyTheme()` (आणि `src/app/layout.tsx` मध्ये inline केलेले `THEME_BOOT_SCRIPT`, जे hydration पूर्वी चालते) `data-theme="dark"|"light"` सेट करते आणि `<html>` वरील `.dark` class एकत्र toggle करते. किटचा dark token set `data-theme="dark"` वर आधारित आहे (`packages/ui-kit/src/ci-tokens.css`); OmniRoute चे स्वतःचे dark overrides (`globals.css` मधील `.dark` block) आणि legacy Tailwind `dark:` utilities `.dark` class वर आधारित आहेत. Accent color presets नाहीत: accent नेहमी kit मधून येतो आणि जुन्या build मधील persisted preset store load झाल्यावर काढून टाकला जातो.
- **Palettes.** दोन, दोन्ही kit मधून (`src/shared/constants/appearancePalette.ts`): `editions`, default, आणि `classic`. Editions म्हणजे `<html>` वरील kit चे `data-ci-appearance="editions"` attribute, जे `ci-editions.css` (`ci-ui.css` मधून imported) `data-theme` सोबत एकत्र वापरते; Classic म्हणजे attribute नसणे. Root layout हे attribute server-render करते, त्यामुळे काहीही stored नसलेल्या (किंवा JS नसलेल्या) visitor ला प्रत्येक surface वर — dashboard, login, `/status`, error pages, `/docs` आणि PWA वर — Editions मिळते. ही निवड theme सोबत त्याच `theme` store मध्ये persisted केली जाते (`src/store/themeStore.ts` मधील `palette`, `setPalette()`, `applyPalette()`) आणि `THEME_BOOT_SCRIPT` द्वारे paint पूर्वी लागू केली जाते (`src/shared/utils/themeBootScript.ts`, layout च्या `<head>` मध्ये inline केलेले); stored palette `"classic"` असतानाच ते attribute काढते. Root layout च्या बाहेर असलेले `src/app/global-error.tsx` ते त्याच store मधून लागू करते. `data-ci-appearance` इतर कोणत्याही element वर ठेवू नका: kit ते `html:root:has([data-ci-appearance="editions"])` सोबत match करते, त्यामुळे एक descendant संपूर्ण document बदलू शकतो. Editions चे `data-ci-editions-variant="landing"` variant marketing pages साठी आहे, dashboard साठी नाही. Browser chrome: server default, Editions, `viewport.themeColor` मध्ये render करतो (`prefers-color-scheme` प्रति एक tag) आणि web manifest मध्येही — `src/shared/constants/pwaThemeColors.ts` मधील `PWA_THEME_COLORS`, Editions च्या `--ci-color-background` (`#f3f1e9` / `#11120f`) चे एकमेव mirror, `tests/unit/pwa-theme-colors.test.ts` द्वारे `ci-editions.css` शी pinned आहे. त्यानंतर live `<meta name="theme-color">` stored palette आणि mode चे अनुसरण करते: `THEME_BOOT_SCRIPT` paint पूर्वी tags पुन्हा लिहिते आणि theme store च्या actions प्रत्येक बदलावेळी ते करते (`src/shared/utils/themeColorMeta.ts` मधील `resolveThemeColor()` / `applyThemeColor()`, तसेच kit च्या `ciTokens` मधून read केलेले `CLASSIC_PAGE_BACKGROUND`). Explicit light/dark theme प्रत्येक tag त्या mode वर सेट करते; `system` प्रत्येक scheme साठी एक colour ठेवते. Manifest Editionsच राहतो: तो प्रत्येक install साठी एकदाच fetch केला जातो आणि preference शिवाय असतो. Monaco आपले colours probe वरून वाचते (`monacoKitTheme.ts`); Editions अंतर्गत probe read एका synchronous pass साठी root `data-theme` बदलते, कारण kit root वरून Editions light/dark resolve करते.
- **Components (adapters).** `src/shared/components/index.tsx` OmniRoute component API (तीच names, default exports आणि props) कायम ठेवते आणि त्यामागील primitives kit वरील adapters आहेत: forms (`Button`, `Input`, `Textarea`, `Checkbox`, `Select`, `Toggle`, `Badge`, `Card`), overlays आणि feedback (`Modal`/`ConfirmModal`, `Tooltip`/`InfoTooltip`, `NotificationToast`, `EmptyState`, `Loading`), structure (`Collapsible`, `CollapsibleSection`, `SegmentedControl`, `Breadcrumbs`, `Avatar`) आणि tables (`DataTable`, `FilterBar`, `ColumnToggle`, `FilterPills`, `PresetSlider`). Adapter kit component ला subpath द्वारे import करतो आणि legacy props त्यावर map करतो — उदाहरणार्थ `Button variant="primary"` हे kit चे `default` button आहे (`--ci-button-primary-*`: light मध्ये inverse surface, dark मध्ये त्याच्या `--ci-color-accent-foreground` ink सह accent), `danger` हे `destructive` आहे आणि `warning` हे `outline` तसेच `.ci-button--warning` extension आहे. `globals.css` च्या शेवटी (`@layer components`) असलेले `.ci-button--warning` आणि `.ci-badge[data-tone]` rules हे kit classes वरील OmniRoute extensions आहेत. `tests/unit/ui/adapters/*.test.tsx` प्रत्येक adapter ला निश्चित करतात.

## 2. नियम

1. लिटरल्स कधीही वापरू नका; नेहमी टोकन्स वापरा. जाणूनबुजून ठेवलेले अपवाद: नेहमी गडद असलेले कन्सोल टर्मिनल आणि
   `STATUS_HEX` (`src/shared/constants/statusColors.ts`), लिटरल हेक्स आवश्यक असलेल्या कॉलर्ससाठी किटच्या स्टेटस

## 5. किट अपडेट करणे

`npm run check:ui-kit-upstream` `packages/ui-kit/UPSTREAM.md` मध्ये पिन केलेल्या आवृत्तीची अपस्ट्रीम रेपोच्या नवीनतम `v*` टॅगशी तुलना करते आणि जेव्हा प्रकाशन संपते तेव्हा सिंक कमांड प्रिंट करते.

दैनिक `UI Kit upstream watch` वर्कफ्लो (`.github/workflows/ui-kit-upstream-watch.yml`) समान तपासणी चालवते. पिन मागे असताना, `scripts/ci/ui-kit-sync-pr.sh` एक सिंक PR सर्वोच्च `release/vX.Y.Z` शाखेच्या विरुद्ध, रोलिंग ब्रांच `chore/ui-kit-sync-latest` वर उघडे ठेवते. हे कधीही विलीन होत नाही: प्रत्येक किट रिलीजला अजूनही स्थानिक VPS वर व्हिज्युअल तपासणी आवश्यक आहे. शाखा पुन्हा तयार केली जाते जेव्हा नवीन प्रकाशन बाहेर येते आणि अन्यथा एकटे सोडले जाते. हाताने पुश केलेल्या कमिटसह उघडलेले PR ओव्हरराइट केले जात नाही आणि एका आवृत्तीसाठी एक PR जो मेंटेनरने बंद केलेला अनमर्ज्ड नवीन रिलीज होईपर्यंत बंद राहतो.

जेव्हा कोणतेही PR उघडले जाऊ शकत नाही (लक्ष्य प्रकाशन गोठलेले आहे, PR ने हाताने ढकलले आहे, PR बंद केले आहे, किंवा कोणतेही PR टोकन सेट केलेले नाही) वर्कफ्लो एक ट्रॅकिंग समस्या उघडे ठेवते जे कारण सांगते.

वर्कफ्लो दोन रहस्ये वापरते:

- `secrets.UI_KIT_READ_TOKEN`: खाजगी अपस्ट्रीम रेपोसाठी केवळ वाचनीय टोकन. जेव्हा वर्कफ्लो अपस्ट्रीम वाचू शकत नाही (कोणतेही टोकन नाही, एक टोकन ज्याने काम करणे थांबवले आहे किंवा GitHub पोहोचण्यायोग्य नाही) रन हिरवा राहतो परंतु एक चेतावणी लिहितो आणि एक वेगळा मुद्दा खुला ठेवतो, जो नंतरच्या रनने पुन्हा अपस्ट्रीम वाचू शकतो तेव्हा तो स्वतःच बंद होतो.
- `secrets.UI_KIT_SYNC_PR_TOKEN`: या रेपॉजिटरीवर सामग्री आणि पुल विनंत्या लिहिण्याच्या प्रवेशासह एक सूक्ष्म टोकन. डीफॉल्ट `GITHUB_TOKEN` येथे PRs तयार करू शकत नाही, आणि PR उघडल्यास CI ट्रिगर होणार नाही. या टोकनशिवाय वर्कफ्लो केवळ शाखेला धक्का देतो.

`scripts/dev/sync-ui-kit.sh <commit|latest> [clone]` त्या कमिटवर अपस्ट्रीम `src/` कॉपी करते (`latest` = नवीनतम `v*` टॅग) `packages/ui-kit/src` मध्ये, सिंगल अनुमत ट्रान्सफॉर्मेशन लागू करते (हे सापेक्ष आयातींमधून `.js` प्रत्यय टाकते), आणि वर्कस्पेस आवृत्ती `packages/ui-kit/package.json` आणि `package-lock.json` मध्ये अपस्ट्रीमवर सेट करते. नंतर: `git diff packages/ui-kit` पुनरावलोकन करा, दोन्ही थीममध्ये प्रदाते, सेटिंग्ज, कॉम्बोज, वापर आणि एंडपॉइंटवर व्हिज्युअल पास करा, `npm run check:ui-kit-snapshot` आणि `npm run test:vitest:ui` चालवा आणि अपस्ट्रीम चेंजलॉगसह PR उघडा.

- **फॉन्ट्स.** GitHub Markdown सोबत CSS येत नाही आणि camo प्रॉक्सी प्रत्येक बाह्य फेच ब्लॉक करते, त्यामुळे किटचा टाइप फाइलमध्येच समाविष्ट असावा लागतो. प्रत्येक जनरेटरची शेवटची पायरी असलेले `scripts/docs/readme-outline.mjs`, HarfBuzz वापरून Switzer भूमिका आकारते आणि त्या व्हेक्टर आउटलाइन म्हणून (`<defs>` पाथ्स आणि `<use>`) रेखाटते; Switzer मध्ये नसलेले बाण आणि भूमितीय चिन्हे त्याच्या स्वतःच्या मेट्रिक्सनुसार रेखाटली जातात. नेहमी आउटलाइनच वापरा, एम्बेड केलेला फॉन्ट कधीही वापरू नका: Switzer चा परवाना (`packages/ui-kit/src/fonts/FFL.txt`) लेखी संमतीशिवाय सबसेटीकरण आणि स्वरूप रूपांतरणास मनाई करतो आणि व्हेक्टर रेखाचित्रांना परवानगी देतो, त्यामुळे Switzer `@font-face` किंवा `data:` URI पुन्हा आणू नका. फाइलमध्ये उरलेला एकमेव फॉन्ट म्हणजे वास्तविक कोड मजकूर म्हणून कायम राहणाऱ्या भागासाठी असलेला OFL IBM Plex Mono सबसेट (`scripts/docs/readme-fonts.mjs`), जो त्या अक्षरांपासून तयार केला आहे; एम्बेड न करता येणारे कोणतेही ग्लिफ आढळल्यास त्रुटी निर्माण होते.
- **पुन्हा जनरेट करणे.** `npm run docs:readme-diagrams` सर्व बारा आकृत्या README मधील क्रमाने पुन्हा लिहिते आणि प्रत्येक फाइलसाठी तिच्या आकारासह एक ओळ प्रिंट करते. एक स्वतंत्र जनरेटरही स्वतः चालतो (`node scripts/docs/gen-readme-<name>.mjs`; `free-tier-budget` साठी `node --import tsx/esm` आवश्यक आहे, कारण त्यातील आकडे `open-sse/config/freeModelCatalog.ts` मधील लाइव्ह कॅटलॉग लोडरमधून येतात; कॅटलॉगमधील बदलाचा CI परिणाम `docs/architecture/QUALITY_GATES.md` → `docs-sync-strict` येथे दिला आहे). जनरेटर आणि SVG एकत्र कमिट करा.
- **पुरावा.** `scripts/docs/readme-svg-shots.mjs <file.svg> <outdir>` ही कमांड GitHub ज्या प्रकारे फाइल सर्व्ह करते त्याच प्रकारे ती रेंडर करते (एक `<img>` टॅग, camo चे `Content-Security-Policy`, `image/svg+xml`), एक फिकट आणि एक गडद फ्रेम कॅप्चर करते आणि पृष्ठाने केलेल्या बाह्य फॉन्ट विनंत्या नोंदवते (त्या 0 असणे आवश्यक आहे).
- **आकारमर्यादा.** प्रत्येक फाइल 200 KB पेक्षा कमी असावी (प्रत्येक कालबाह्यता चाचणी हे तपासते); कोणत्याही README प्रतिमेसाठी 500 KB ही कठोर कमाल मर्यादा आहे (SVG स्टुडिओ व्हॅलिडेटरचा नियम).
- **मजकूर अपरिवर्तित, आकडे गेटमधून.** रीब्रँडमध्ये टाइप आणि पॅलेट बदलले, शब्द नाहीत: प्रत्येक जनरेटर त्याच्या आकृतीचा मजकूर `*_COPY` स्थिरांकात ठेवतो (किंवा लाइव्ह कॅटलॉगमधून तयार करतो), जो रेखाटलेला मजकूर आणि आउटलाइनिंग पायरीचा इनपुट अशा दोन्ही स्वरूपांत वापरला जातो. प्रमाणित आकडे `<text>` नोड्समध्ये राहतात (आउटलाइन केल्यानंतर अदृश्य, `fill-opacity:0`) आणि `check:docs-counts`
  (`scripts/check/check-docs-counts-sync.mjs`) द्वारे वाचले जातात; गेट ज्या आकृत्या वाचते त्यांच्या कालबाह्यता चाचण्या जनरेट केलेल्या फाइलवर त्याचे व्हॅलिडेटर्सही चालवतात, त्यामुळे कोडपासून विचलित झालेला आकडा चाचणी अपयशी करतो — जनरेटरमधील संख्या कधीही बदलू नका; त्याऐवजी गेट वाचत असलेला स्रोत दुरुस्त करा.
